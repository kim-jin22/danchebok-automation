## 0. 하네스 엔지니어링으로 다루는 법 (메타 규칙)

> 하네스 엔지니어링 = AI와 안정적으로 함께 일하도록 규칙·구조·검증을 설계하는 방법론.
> **원칙: 작게 시작하고, 과적합하지 않는다.** 단일 HTML 프로토타입 규모에 맞게 가볍게 적용한다.

- **① 지시문서** — 이 md가 규칙·용어·업무 흐름의 단일 진실 소스. 새 세션마다 먼저 읽히고 처음부터 다시 설명하지 않는다.
- **② 아키텍처 제약** — 구현/디자인 규칙을 컨벤션으로 고정하고, 재사용 로직(게이트 검증·자릿수 검증·표준단가)을 별도 함수로 분리해 중복·실수를 막는다.
- **③ 피드백 루프** — 각 관문에서 시스템이 조건을 자동 판정한다. "관문을 통과 못 하면 다음으로 못 넘어간다"가 곧 센서 역할.
- **④ 지식 저장소** — 진행 상황을 `progress.md`에 기록한다. 무엇을 했고, 다음에 뭘 할지, 막힌 지점을 남긴다.

**의도적으로 안 쓰는 것(과적합 방지):** Subagents·Hooks·MCP는 단일 HTML 프로토타입엔 과하다. 규모가 커지면 도입.

## 1. 프로젝트 개요

- **무엇:** 단체복 B2B 커머스의 반복업무 사고를 예방하는 자동화 시스템 (익명 사례 연구)
- **왜:** "사람이 기억해야 사고가 안 나는 구조"를 "시스템이 막아주는 구조"로 전환
- **산출물:** 단일 HTML 인터랙티브 대시보드 (백엔드 없음, 가상 샘플 데이터)
- **배경:** 작성자가 단체복 커머스(익명)에서 담당한 업무 — 상품 등록·발주·CS

## 2. 도메인 맥락 (고정 지식)

업무 흐름: `주문 → 시안 → 시안수정·확정 → 결제 → 의류 발주 → 인쇄 발주 → 배송`
- 한 주문을 진행담당자(상담·발주)와 디자이너(시안·인쇄)가 나눠 맡음
- 배턴이 담당자→디자이너→담당자→디자이너로 **두 번** 넘어가며, 사고는 이 지점에서 발생
- 결제는 시안 확정 이후에만 가능. 인쇄 없는 건은 시안 단계를 건너뜀

반복 사고 진원지: S1 핸드오프 누락 · S2 견적/단가 오류 · S3 결제/미수금 · S4 공급처 파편화 · S5 재고/납기 · S6 인쇄방식 매칭 · S7 인쇄 사고
→ 공통 원인: "필요한 확인을 사람이 기억해야 한다" → 해법: 확인을 시스템의 필수 관문으로.

## 3. 만든 것

- **주문접수 자동 분류(트리아지)** — 신규 접수를 14단계로 자동 검증 → 정상 이관 / 문제 상담
- **진행단계 자동 처리** — 관문 통과 건 자동 진행 / 문제 건 자동 보류
- **M2 핸드오프 게이트** — 진행상태 변경 시 조건 자동 판정, 전부 통과해야 이동
- **M3 견적 자릿수 검증** — 매뉴얼 표준단가 대비 자릿수 감지
- **도메인 사고 방지** — 나염 판 만료·자수 회유/판 보유·추가건 진위·위치↔크기 교차검증
- **검증(감사) 탭** — 통과 근거 로그 + 현재 상태 재검증

## 4. 구현 규칙

- 단일 HTML 파일 (HTML+CSS+JS). 외부 백엔드·DB 없음
- 데이터는 JS 내 가상 샘플 배열 (실제 거래처·단가·실명 금지 — 익명 사례)
- 상태는 브라우저 메모리(JS 변수)로만 관리
- 라이트 톤 · 포인트색 절제 · 수치는 차트로 · 정보 우선순위대로 배열

## 5. 원칙

- **루틴은 자동, 예외만 사람.** 조금이라도 애매하면 통과가 아니라 상담으로 (Fail-safe).
- **사실은 촘촘하게, 판단은 사람에게.** 규칙은 객관 사실에만 걸고, 주관 판단은 상담으로 라우팅.
- **가드는 벼랑 끝에만.** 모든 예외를 규칙화하려는 순간이 곧 과적합 신호 → 상담으로.
